---
title: 'Booking system workflows (A / B / C)'
description: 'Different booking systems need different call sequences. Pick the workflow from `farePrices.bookingSystem`, then follow the right A, B, or C steps.'
---

Every fare carries a `bookingSystem` value under `farePrices[].bookingSystem`. That value determines which API call sequence you must follow to configure, price, and book the product. Three workflows exist:

| `bookingSystem` | Workflow | Notes |
| --- | --- | --- |
| *(null / missing)* | **A** | Pre-tagged rows. Safe default. |
| `Generic` | **A** | Lowest-common-denominator shape for external integrations. |
| `Clockwork` | **A** | |
| `CMS` | **A** | |
| `SOAAccommodation` | **A** | |
| `Rezdy` | **A** | Added 2026-10. Same two-call shape as Generic — TDMS native integration to Rezdy. PPDIDs that previously appeared as `Generic` are being progressively retagged. |
| `Respaxv2` | **B** | |
| `IBIS` | **B** | |
| `CustomLinc` | **B** | |
| `Fareharbor` | **C** | Added 2026-10. New flow — see below. |

Always branch on `farePrices.bookingSystem` BEFORE choosing a workflow. Treat unknown or missing values as Workflow A (safe default).

## Workflow A — Standard booking systems

`Generic` · `Clockwork` · `CMS` · `SOAAccommodation` · `Rezdy`

```
1. GET /apiv1/bookingdetails/{productPricesDetailsId}
            ↓
2. GET /apiv1/checkavailabilityrange/{productPricesDetailsId}/{timeId}/{startDate}/{days}?cached=1
```

**Step 1** returns the configurable fields for the fare — booking times, pickup locations, optional fields, supplier info. The schema is essentially static per PPDID; cache aggressively (we hold a 24h TTL per `(branch, env, ppdid)`).

**Step 2** returns live availability for the picked `timeId` on `{startDate}` + the next `{days}` days. Add `?cached=1` for the cached result (lower latency, acceptable for most read-paths). Omit it (or `cached=0`) when you need a real-time number — e.g. just before placing an order.

<Info>
TDMS's `/checkavailabilityrange` requires the date segment in `DD-Mon-YYYY` format. ISO dates are rejected with a misleading 400 error (`"ProductPricesDetail ... is not a valid price."`). The sibling `/detailsToConfirmAvailability` endpoint accepts ISO — only this one is fussy.
</Info>

## Workflow B — Enhanced booking systems

`Respaxv2` · `IBIS` · `CustomLinc`

```
1. GET /apiv1/checkavailabilityrange/{productPricesDetailsId}/0/{startDate}/{days}?cached=1
            ↓
2. GET /apiv1/bookingdetails/detailsToConfirmAvailability/{productPricesDetailsId}/{date}/{timeId}
```

**Step 1** uses `timeId=0` as a sentinel — tells the enhanced systems "give me availability and the time selector inline". The response includes:

- A `fields[]` array. For Respax / CustomLinc multi-time products, the `fields[name=timeId]` entry carries selectable `options` (each with `externalId` + `displayName` + `numAvailable`). For single-time Respax / CustomLinc the inline `BookingTimeID` IS the time, and `pickupId` / `dropoffId` fields are populated inline from the same response. For IBIS, step 1 returns an empty `fields[]` plus a top-level `BookingTimeID` session key — you'll need step 2 to resolve pickups / dropoffs.
- A `RequiresFurtherDetailsToConfirm: true` flag indicating you must call step 2 before placing an order.

**Step 2** uses the specific `timeId` from step 1 to retrieve the pickup / dropoff / optional-field set for that particular time slot. Supplier option sets can vary per-time, so always scope by `timeId` rather than unioning across times.

## Workflow C — FareHarbor

`Fareharbor` *(added 2026-10)*

FareHarbor has a richer native API than Generic / Rezdy. Optional fields can be time-dependent AND can affect the final price (`isPriced=true`), which means every booking needs a dedicated **reservation lock** before you can POST `/order`.

```
1. GET /apiv1/checkavailabilityrange/{productPricesDetailsId}/0/{startDate}/{days}?cached=1
            ↓
2a. If step 1 did NOT return a fields entry whose name is timeId:
    GET /apiv1/bookingdetails/detailsToConfirmAvailability/{productPricesDetailsId}/{date}
    (no timeId segment) — select an options.externalId from the returned timeId field
            ↓
2b. GET /apiv1/bookingdetails/detailsToConfirmAvailability/{productPricesDetailsId}/{date}/{timeId}
    — select / enter every required optional field
            ↓
3. GET /apiv1/checkAvailability/{productPricesDetailsId}/reservation
   — pass bookingTimeId, bookingDate, and each selected / entered field
            ↓
4. POST /apiv1/order with datePriceCacheId on each affected product + booking
```

**Step 1** — same shape as Workflow B's step 1. If the response includes `fields[name=timeId]` with options, skip to step 2b.

**Step 2a** — details WITHOUT a timeId segment. Pull `fields[name=timeId]` from the response; each `options.externalId` is a selectable time.

**Step 2b** — details WITH the picked timeId. Returns the pickup / dropoff / optional-field set for that specific time. Inner field names beginning `optionalFields_bl_` are **booking-level** (one per booking); names beginning `optionalFields_cl_` are **customer-level** (one per passenger). Fields can be priced or non-priced (`isPriced=true` on priced ones).

**Step 3 — reservation lock.** Call `/apiv1/checkAvailability/{ppdid}/reservation` with:

- `bookingTimeId` + `bookingDate`
- Every selected / entered optional field as paired, explicitly indexed entries:
  - `additionalFields[0][optionalFieldId]` + `additionalFields[0][fieldText]`
  - `additionalFields[1][optionalFieldId]` + `additionalFields[1][fieldText]`
  - etc.
  - Send `options.externalId` for select / radio fields; send typed text for text fields.
- All required fields, all priced selections (`isPriced=true`), and lodging MUST be sent. Non-priced optional answers can be deferred to the order itself.

The response carries a `datePriceCacheId` and the final `rrp`. The `datePriceCacheId` is bound to this exact combination of `(date, timeId, priced selections, lodging)` — do NOT reuse it for a different date, time, priced selection or lodging.

**Step 4 — order.** POST `/apiv1/order` with the `datePriceCacheId` from step 3 on BOTH the product record AND each booking record. Non-priced answers can be added or changed in the order payload without re-running step 3.

<Info>
**Price-cache lifetime.** Treat `datePriceCacheId` as single-use for the specific locked combination. If the customer changes date, time, a priced optional field, or lodging after step 3, you MUST call step 3 again to lock a fresh id. Non-priced changes (comments, notes) can ride on the existing id.
</Info>

### Example — step 2b response (abridged — large lodging list truncated)

Note the **nested shape**: the outer `fields[]` has one wrapper entry (`name: "optionalFields"`), and the actual field list is inside `fields[0].fields[]`. Each inner field carries `isPriced` (all false here — this product has no priced extras).

<Warning>
**Per-passenger field duplication for multi-pax fares.** On a 2-pax fare like Prima's "Private Double Cabin (Sleeps 2 guests)", TDMS encodes "ask this question for each passenger" by **repeating the field entry** in `fields[0].fields[]`. The real step-2b response for this product shows `optionalFields_cl_710104` (Dietary Requirements) listed TWICE — once between the Full Name entries, once after `cl_690457` ("Full Name of Second Passenger"). The supplier is pre-indexing per-passenger slots.

Parsers must decide: dedupe by `name` (ignoring the per-pax intent, treating repeat entries as noise) or preserve the duplicates (rendering each occurrence as a separate input). For the single-redeemer `/order` path (each addon purchased as qty=1), deduping is safe. For a multi-pax fare where the fare itself covers N guests, each occurrence should get its own answer. The reservation lock and `/order` manifest both appear to behave the same regardless (both 4-field and 5-field variants of this product returned the SAME `datePriceCacheId` from `/reservation`).
</Warning>

<Info>
**Cache ids are DETERMINISTIC, not time-bound tokens.** TDMS returns the same `datePriceCacheId` for the same `(ppdid, date, timeId, selection fingerprint)` across repeated calls. For products with no `isPriced` options, further-adding non-priced fields often yields the SAME id (verified against Prima Whitsunday — 4 vs 5 fields both returned `13119045`). <Warning>
**Cache ids differ across endpoints — use the right source.** For the SAME `(ppdid, date, timeId)` the three endpoints returned three different ids in our verification (per-PPDID `/checkavailabilityrange?cached=1` → `13119087`; bulk `/checkAvailabilityProduct` → `12938709`; `/reservation` minimal → `12938709`). **Always source the id for `/order` from `/reservation`** (or an uncached `/checkAvailabilityProduct`). The `?cached=1` step-1 id is a snapshot id for display only — do NOT thread it onto `/order`.
</Warning>

<Warning>
**The step-1 cache id can only be reused on `/order` when zero additionalFields accompany the booking.** The moment any field answer is sent (lodging, Full Name, Dietary — anything, even non-priced), you MUST call `/reservation` first and use the id it returns. Sending a stale or wrong id with populated additionalFields produces a 400 "FareHarbor options for (date) do not match the confirmed price" from TDMS — do NOT attempt a fallback, abort the submission and re-run `/reservation`.
</Warning>

### Example — step 3 error response (bad lodging externalId)

HTTP 500 — thrown when a submitted option externalId isn't in the server's current option list (either a crafted request OR operator-side drift between page load and submit). The supplier context ("company shortname") is leaked in the message — sanitise before surfacing to end users.

```json
{
  "code": null,
  "errors": [],
  "message": "Reservation check failed, not bookable. Reason: 99999 is not a valid lodging pk for company shortname 'explorewhitsundays'",
  "status": "error",
  "statusCode": 500,
  "statusText": "Internal Server Error"
}
```

<Warning>
**`additionalFields` and `optionalFields` are DIFFERENT fields in DIFFERENT places** — easy to conflate:

- **Step 3 `/reservation`** — selections go as URL **query params** named `additionalFields[i][optionalFieldId]` + `additionalFields[i][fieldText]`.
- **Step 4 `/order`** — the same selections go as a JSON **body** property named `bookings[0].optionalFields: [{optionalFieldId, fieldText}, ...]`. **Same key name as Workflow A/B** — not `additionalFields`.

Sending `bookings[0].additionalFields: [...]` on `/order` for a Fareharbor product means TDMS reads zero recognised answers and rejects with "FareHarbor options for (date) do not match the confirmed price" even when `/reservation` succeeded with the identical selections — because the reservation lock expected N field answers to accompany the order and the `additionalFields` key is silently ignored (like `fieldValue` is on A/B).
</Warning>

<Warning>
**`datePriceCacheId` MUST be mirrored on BOTH the per-redeemer product record AND each booking record.** Setting it on only one is a rejection path. The step-4 example below shows both — keep them in lockstep.
</Warning>

<Info>
**When can `/reservation` be skipped?** Only when the operator/customer provided NO additionalField answers at all. In that case, thread the step-1 `datePriceCacheId` straight to `/order`. Any field selection — including non-priced ones — requires a fresh `/reservation` call.
</Info>

<Warning>
**Fareharbor /order shape differs from Workflow A/B in seven ways:**

1. **`datePriceCacheId` on THREE positions** — top-level `products[]`, per-redeemer `products[]`, each `bookings[]`. All must be the same id from the preceding `/reservation`.
2. **`productPricesDetailsId` as STRING at both top-level and per-redeemer levels.** Workflow A/B sends it as a number at the top level; Fareharbor needs string everywhere.
3. **`pickupId: "0"` on each booking** — literal string "0" even though Fareharbor uses lodging (sent via step-3 reservation), not a pickup. TDMS treats missing `pickupId` as "resolve from the slot definition" which may fail for Fareharbor's grouped-booking semantics.
4. **`optionalFields: null`** on the per-redeemer product (literal null, not an empty array). This is the DIFFERENT slot from the booking-level `optionalFields` (point 7) — same key name, different position, different meaning.
5. **`bookWithFirstRedeemer: false`** on each per-redeemer product.
6. **Multi-passenger is N REDEEMERS, not N bookings on one redeemer.** Each additional passenger is a new entry in `redeemers[]` with its own `products: [{ redeemerQty: 1, bookings: [{...}] }]`. Top-level `qty` = sum of all redeemers' `redeemerQty`.
7. **Field answers go on `bookings[0].optionalFields` — SAME key name as Workflow A/B.** The step-3 reservation URL uses `additionalFields[i][optionalFieldId]/[fieldText]` query params; on `/order` the body carries the same selections under `optionalFields: [{optionalFieldId, fieldText}, ...]`. **Do NOT use `additionalFields` on `/order` for Fareharbor** — TDMS silently ignores it (same contract as `fieldValue` being ignored for A/B) and the reservation lock then rejects the order with "options do not match the confirmed price" because the locked set couldn't be matched to any submitted answers.
</Warning>

### Example — step 4 error response (price mismatch)

HTTP 400 — thrown when TDMS's manifest layer can't match the order's optionalFields to the selection set locked by `/reservation`. Causes we've reproduced:

1. **Wrong key name on the booking** — using `additionalFields: [...]` instead of `optionalFields: [...]`. TDMS silently ignores the wrong key, so from its view the order carries zero recognised answers; the locked set then fails to match. (Also the trap: step-3 `/reservation` URL uses `additionalFields[i][...]` query params, which doesn't translate to the body shape on `/order`.)
2. **Wrong `datePriceCacheId`** — using the snapshot id from `?cached=1` step-1, or a stale id from a prior selection set.
3. **Selection set drift** — the lock was minted against selection set X, but the order submits selection set Y.

```json
{
  "code": null,
  "errors": [],
  "message": "Product 'Prima - 2 day 1 night Whitsunday Sailing' FareHarbor options for (20-Oct-2026) do not match the confirmed price. Please recheck the reservation and use the returned datePriceCacheId.",
  "status": "error",
  "statusCode": 400,
  "statusText": "Bad Request"
}
```

Remediation: confirm `bookings[0].optionalFields` (not `additionalFields`) is being sent with the exact same entries sent to `/reservation`, and that `datePriceCacheId` on `/order` is the id just returned from `/reservation` (not from `?cached=1` step-1).

### Workflow C implementation invariants

The following apply when building a Workflow C integration against a multi-branch TDMS setup (one branch's tour products pointing to another branch's addon/payment account via `addon_branch_code`). Learned the hard way during Phase C of the Group Booker Addon Portal integration — all have test coverage in that project.

<Warning>
**1. All TDMS calls for a single Fareharbor booking MUST use the SAME TDMS identity.** `/checkavailabilityrange` + `/detailsToConfirmAvailability` (step-2b) + `/reservation` + `/bookingreference` + `/order` all need to authenticate under the SAME branch's TDMS account. The `datePriceCacheId` is **account-scoped**; a lock minted under branch A and sent to `/order` under branch B is rejected. For cross-branch setups, resolve the addon-side branch at the top of the request handler and route every TDMS call through those creds.
</Warning>

<Warning>
**2. Call `/reservation` BEFORE `/apiv1/bookingreference`.** TDMS mints a bookingReference on demand; it's a bookable "slot" against the account. If `/reservation` fails for any reason (step-2b drift, bad lodging, Fareharbor rejection), you'll have burned an unused bookingReference. Order: `/reservation` → `/bookingreference` → `/order`. The reference itself does not need to be known to `/reservation`.
</Warning>

<Warning>
**3. Validate the submitted selection set against the step-2b schema BEFORE calling `/reservation`.** `/reservation` will accept selections TDMS considers "well-formed," but a drifted operator config (field removed, option retired) between the customer's page load and submit can still land there. Catch unknown field names, forged option externalIds, missing required fields, and missing-when-required lodging server-side upfront — surface a specific 400 to the customer. The step-2b response is the authoritative schema at the moment of submit.
</Warning>

<Info>
**4. Picker-side TDMS reads must use the addon branch identity too.** For a lazy-hydration customer portal (step-1 availability + step-2b fields fetched when the page loads), use the SAME identity those two picker-side calls will later use at `/select`/`/reservation`/`/order`. Mismatch produces the "customer sees branch A's schema but branch B's `/select` validator re-fetches a different schema and rejects a valid-looking answer" bug class.
</Info>

<Info>
**5. qty / redeemer model: a Fareharbor booking is N redeemers × (redeemerQty: 1), not one redeemer × bookings[N].** Each passenger becomes a separate `redeemers[]` entry with its own `products[0].bookings[0]`. Top-level `products[0].qty` = sum of each redeemer's `redeemerQty`. Single-passenger addon flows collapse to one redeemer with `qty: 1`.
</Info>

## What stays the same across all three workflows

Only the **request-side call sequence** varies by workflow. Everything downstream of a successful order is identical:

- **`POST /apiv1/order` response envelope** — order-level, not product-level. The shape returned after submission is the same whether the booking was Workflow A, B, or C. A Fareharbor product on an order responds with the same confirmation / booking-reference / voucher structure as a Generic product. Parse once, works everywhere.
- **Error envelopes** — error shapes are generic across all workflows. Any `/apiv1/*` call that returns a 4xx / 5xx surfaces the same payload format regardless of the fare's `bookingSystem`. Workflow-specific nuances live only in which calls you make, not in what comes back when something fails.

So Workflow C's additional complexity is contained to the request side — what you SEND to configure, lock price, and build the order payload. The response-parsing + error-handling you already have for Workflow A / B keeps working untouched.

## Implementation tips

- **Always inspect `farePrices.bookingSystem` first.** Routing on anything else drifts the moment TDMS re-tags a product.
- **Treat unknown / missing values as Workflow A** — safe default, matches pre-tagged rows.
- **Cache `/bookingdetails` responses per PPDID.** The schema is essentially static; a 24h TTL per `(branch, env, ppdid)` eliminates per-click round-trips.
- **Use `?cached=1`** on `/checkavailabilityrange` for most read-paths. Omit (or set `cached=0`) when the availability number itself is load-bearing (right before an order).
- **FareHarbor price-cache**: always use the `datePriceCacheId` from the final `/reservation` call — it reflects the chosen priced options. Reusing an older id against a changed selection will return wrong pricing on the final booking.
- **Watch for `RequiresFurtherDetailsToConfirm` and `RequiresReservationCheck` flags** in step 1 / step 2 responses. Both are explicit "you need another call before you can order" signals.
